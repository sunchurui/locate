# Rex-token object credit prototype

This is an opt-in extension of the existing Rex-Omni GRPO trainer with the existing GroundingPI-inspired reward adaptation. It does not change the response reward or sampling. After the existing GRPO advantage calculation, it adds `object_credit_weight * local_credit` to selected generated-token advantages. The default is disabled; enabling requires the GRPO estimator. The default coefficient is 0.1, not a guarantee that the final advantage changes sign.

The integration patch in `object_credit_integration.patch` applies to the trainer **after** the existing `rex_groundingpi.patch`; `object_credit.py` is installed in `references/Rex-Omni/finetuning/verl/trainer/`. No training task is submitted. The linked local script `check_object_credit.py` is a small optional CPU integration check.

Configuration knobs in `algorithm`:

* `object_credit_enabled=false`: opt in with `true`.
* `object_credit_weight=0.1`: scalar residual coefficient.
* `object_credit_complete_gt=false`: set to true only for annotations you have explicitly verified to be sufficiently complete; this enables negative credit for unmatched valid predictions and missed GTs. COCO excludes crowd and can omit instances: this is an experimental assumption, not a completeness guarantee.
* `object_credit_allowed_labels=null`: no class penalty unless a known exhaustive label list is supplied; `coco80` uses the canonical 80 COCO labels, or supply a comma-separated list. This checks vocabulary membership, not a semantic swap between two valid categories.

The code uses the original output IDs and saved tokenizer. Rex marker tokens and coordinate tokens must each be single tokens. `Rex` output uses coordinate bins 0..999; GT from the existing GroundingPI plugin is in 0..1000 and predictions are scaled accordingly. Same-class predictions and GT are assigned via maximum total IoU Hungarian matching; edges with IoU 0 are discarded after matching. A matched box's four coordinate tokens receive IoU as local credit; a valid unmatched box receives -1 only when complete GT is explicitly assumed. Invalid geometry and unparseable responses receive no local correction. An unrecognized category receives -1 on the category tokens only when allowed labels are provided. A known category's last `<|box_end|>` receives negative missing fraction for that category, and entirely absent categories are credited to actual EOS, only for complete GT and an actual emitted EOS. A truncated output receives no missing/stop credit. Without an EOS there is no stop supervision. Assignment using any positive IoU is a preliminary heuristic: small overlaps, crowded scenes and ambiguous identity can yield wrong labels, and the method does not claim that all unmatched outputs are true duplicates. Matching maximizes IoU and does not enforce first-occurrence selection for duplicates.

The local residual is not a probability of correctness or a calibrated advantage. A positive IoU residual can strengthen an imprecise matched prediction; an unmatched -0.1 contribution may leave its final token advantage positive. `object_credit/*` metrics count parsing and attribution events; the loss and total trajectory reward stay unchanged, and this module is only attached to the actor's advantages. No within-response centering or rollout-relative local normalization is performed. This is not MCR-GRPO's leave-one-out contribution or its complete reward setup.

## Existing blockers: do not submit this as a runnable job

The parent adaptation is not a runnable Qwen3-VL LoRA RL recipe. It still lacks compatible Qwen3-VL multimodal RoPE, loading and training the Rex-token SFT LoRA/tokenizer and reference adapter, data conversion to the upstream dataloader, a working validation path, and a verified environment. The original `groundingpi_reward.py` parses JSON predictions. A separate `rex_groundingpi_reward.py` now supports the current Rex marker outputs while preserving the existing two scoring components; it must be selected explicitly. See `REX_REWARD_README.md`. `ground_truth` must be supplied in the form accepted by the existing reward plugin and already align with the rollout batch.

On October 30, 2026, the trainer/module/config passed Python syntax compilation and the model tokenizer configuration was found to register the four marker strings. The optional actual-tokenizer integration check was started twice but stalled on the login node during initialization and was stopped; no successful real-tokenizer, GPU, optimizer-step, or end-to-end validation has yet been established.
